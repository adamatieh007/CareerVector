1. Shared Retrieval Contract

Both retrieval methods consume the same CareerProfile and return ranked occupation records with scores and metadata. This allows the UI and evaluation code to switch engines without changing the rest of the application.

flowchart LR P["CareerProfile"] --> A{"Retriever"} A -->|tfidf| T["TFIDFModel"] A -->|embeddings| E["EmbeddingModel"] T --> R["Recommendation[]"] E --> R R --> UI["UI / CLI / Evaluation"]

2. TF-IDF Engine

flowchart TD P["Structured profile"] --> Q["Weighted lexical query"] Q --> V["Saved TF-IDF vectorizer"] V --> QV["Sparse query vector"] DOC[("Occupation TF-IDF matrix")] --> CS["Cosine similarity"] QV --> CS CS --> POS["Positive relevance score"] A["Avoid preferences"] --> AV["TF-IDF avoid vector"] AV --> ACS["Avoid similarity"] DOC --> ACS ACS --> PEN["Penalty"] POS --> FINAL["final score"] PEN --> FINAL

TF-IDF is a lexical baseline: it excels when profile wording overlaps the occupation corpus directly. Repetition or weighting in the generated query is intentional because term frequency contributes to the representation.

3. Sentence Embedding Engine

flowchart TD P["Structured profile"] --> NL["Natural-language profile"] NL --> M["SentenceTransformer"] M --> Q["Normalized dense query vector"] D[("Precomputed occupation embeddings")] --> S["Dense cosine similarity"] Q --> S S --> POS["Positive semantic relevance"] A["Avoid preferences"] --> ANL["Natural-language avoid query"] ANL --> M2["SentenceTransformer"] M2 --> AQ["Avoid vector"] AQ --> AS["Semantic avoid similarity"] D --> AS AS --> PEN["Penalty"] POS --> FINAL["final score"] PEN --> FINAL

The embedding model uses semantic proximity rather than exact token overlap. A phrase such as “radiation treatment planning” can therefore retrieve related occupations even if an occupation description uses different wording.

4. Scoring Pipeline

flowchart LR R["Raw relevance"] --> AP["Avoid penalty"] AP --> C["Constraint checks"] C --> S["Sort descending"] S --> K["Top-K results"] K --> X["Explanation metadata"]

The current conceptual scoring rule is:

final_score = positive_similarity - avoid_weight * avoid_similarity

Salary is then applied as a hard constraint when requested. This separation keeps semantic relevance and structured business rules distinct.

5. Query Construction Differences

6. Embedding Build Strategy

flowchart TD O["Semantic occupation document"] --> L{"Long document?"} L -->|No| E["Encode document"] L -->|Yes| C["Split into overlapping chunks"] C --> CE["Encode each chunk"] CE --> AVG["Mean-pool chunk embeddings"] E --> N["L2 normalize"] AVG --> N N --> STORE[("occupation_embeddings.npy")]

Chunking prevents long O*NET records from being silently truncated in a way that overweights the beginning of an occupation record.

7. Future Hybrid Retriever

flowchart LR Q["User profile"] --> TF["TF-IDF score"] Q --> EM["Embedding score"] TF --> N1["Normalize"] EM --> N2["Normalize"] N1 --> H["Weighted fusion"] N2 --> H H --> F["Constraints"] F --> R["Hybrid ranking"]

A later version can fuse lexical and semantic evidence. This is preferable to immediately deleting the TF-IDF baseline, because specific terms such as FPGA, dosimetry, or CUDA can be valuable exact-match signals.
