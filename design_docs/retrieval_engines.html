1. Shared Retrieval Contract

TF-IDF and sentence embeddings return the same general recommendation shape. RAG consumes the embedding results rather than implementing a third independent ranking algorithm.

flowchart LR P[CareerProfile] --> S{Retriever} S -->|TF-IDF| T[TFIDF model] S -->|Embeddings| E[Embedding model] T --> R[Recommendation list] E --> R R --> UI[Direct UI] R --> C[RAG context builder]

2. TF-IDF Engine

flowchart TD P[Structured profile] --> Q[Weighted lexical query] Q --> V[Saved vectorizer] V --> QV[Sparse query vector] MAT[(Occupation TF-IDF matrix)] --> CS[Cosine similarity] QV --> CS A[Avoid query] --> AV[Avoid sparse vector] AV --> AS[Avoid similarity] MAT --> AS CS --> F[Final relevance] AS --> F F --> C[Salary constraint] C --> K[Top K]

3. Sentence Embedding Engine

flowchart TD P[Structured profile] --> N[Natural semantic query] N --> M[SentenceTransformer] M --> Q[Normalized query vector] D[(Precomputed occupation vectors)] --> S[Dot product cosine] Q --> S A[Avoid concepts] --> AQ[Semantic avoid vector] AQ --> AS[Avoid similarity] D --> AS S --> F[Final relevance] AS --> F F --> C[Salary constraint] C --> K[Top K]

4. Why RAG Uses Embedding Retrieval

The current RAG mode uses sentence embeddings because the generator benefits from semantically relevant evidence even when user wording differs from O*NET wording. TF-IDF is still retained as an interpretable baseline and future hybrid signal.

5. Shared Scoring Rule

final_score = positive_similarity - avoid_weight * avoid_similarity

Salary filtering is applied as a hard constraint. RAG does not change this ranking rule; it explains the surviving retrieved evidence.

6. Retrieval versus Generation

flowchart LR Q[User profile] --> RET[Retrieval] RET --> TOP[Top K occupations] TOP --> DIRECT[Direct recommendation view] TOP --> GEN[Generation context] GEN --> LLM[Local LLM] LLM --> EX[Explanation]
The LLM is not the ranker. This separation is central to the design and to evaluation.
