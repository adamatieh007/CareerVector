UI & Request Flow

Three-mode Streamlit flow, local model discovery, request dispatch, and evidence-first RAG presentation.

1. Three-Mode Interaction

flowchart TB U[User] --> M{Select mode} M --> T[TF-IDF] M --> E[Sentence Embeddings] M --> R[RAG Embeddings plus Local LLM] U --> P[Profile inputs] U --> S[Salary and top K] R --> O[Ollama server and model selector] P --> SUB[Find my careers] S --> SUB O --> SUB

2. Profile Inputs

The frontend collects major/background, interests, specializations, preferred work, avoid preferences, optional minimum salary, and top-K result count. The same CareerProfile object is used by all three modes.

3. RAG Model Discovery

4. Submit Flow by Mode

flowchart TD SUB[Submit] --> V[Validate profile] V --> M{Mode} M -->|TF-IDF| T[Load TF-IDF model] M -->|Embeddings| E[Load embedding model] M -->|RAG| RG[Load embedding model plus Ollama client] T --> RR[Ranked results] E --> RR RG --> ADV[RAGCareerAdvisor] ADV --> RA[Generated analysis plus sources] RR --> CARDS[Result cards] RA --> ANSWER[RAG answer] RA --> CARDS

5. Result Presentation

Direct retrieval modes show ranked cards. RAG mode first shows the generated analysis and generator/retriever metadata, then shows the retrieved occupation cards as inspectable evidence. The cards include wage data, related titles, interests, skills, knowledge, work activities, tasks, and software/technology fields when available.

6. UX Rules

  • Always identify the active mode.
  • Never present cosine similarity as model confidence.
  • Keep local-model errors actionable with ollama pull <model> guidance.
  • Preserve retrieved evidence beneath RAG output rather than hiding it.
  • Keep salary constraints explicit because a strict wage filter can produce zero results even when semantic matches exist.
