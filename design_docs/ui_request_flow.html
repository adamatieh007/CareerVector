1. Interaction Model

The Streamlit frontend is a thin presentation layer. It gathers structured answers, creates a CareerProfile, dispatches to the selected retriever, and renders standardized recommendation objects.

The model choice should remain visible during and after ranking so users can deliberately A/B test the same profile.

5. Result Card Contract

classDiagram class Recommendation { +int rank +string occupation_title +string onet_soc_code +float relevance_score +float median_wage +float mean_wage +string related_titles +string matched_terms +string engine +string description }

The renderer should depend on a common recommendation shape. Model-specific explanation details can be optional while the rest of the UI remains identical.

6. UX Rules

  • Do not label cosine similarity as probability. A relevance score is not a confidence percentage.
  • Show selected engine. Every result page should clearly state whether TF-IDF or embeddings produced the ranking.
  • Keep salary optional. Users should be able to inspect relevance before adding hard compensation constraints.
  • Explain empty results. Distinguish “no semantic match” from “matches existed but salary filtering removed them.”
  • Preserve user inputs. Model switching should not clear the profile, enabling immediate side-by-side experimentation.

7. Recommended Future UI Feature

Add a comparison mode that executes both engines for one profile and displays overlap, rank movement, and score differences. This would turn the frontend into a demonstration of retrieval-system design rather than only a career quiz.
