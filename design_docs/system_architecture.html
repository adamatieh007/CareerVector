1. Architectural Goals

CareerVector is structured as a small recommendation platform rather than a single model script. The core goal is to isolate user-profile construction, data preparation, retrieval, constraints, and presentation so changes to one layer do not force changes across the entire application.

5. Offline Build Path

flowchart LR A["download_data.py"] --> B["Raw O*NET CSVs<br/>BLS XLSX"] B --> C["build_dataset.py"] C --> D["data/processed/occupations.csv"] D --> E["train_tfidf.py"] D --> F["build_embeddings.py"] E --> G["TF-IDF artifacts"] F --> H["Embedding artifacts"] G --> I["Runtime"] H --> I
Runtime recommendation should not rebuild the corpus or refit either model. Expensive work is intentionally moved into reproducible offline scripts.

6. Non-Functional Requirements

  • Determinism: the same corpus and model version should produce stable results for the same profile.
  • Low operational cost: no paid cloud service is necessary for the baseline product.
  • Fast interaction: precomputed occupation vectors keep UI-time work limited to encoding one query and ranking ~1K candidates.
  • Auditability: model metadata and data release identifiers should be retained with generated artifacts.
  • Replaceability: a future retriever should implement the same recommendation contract used by the UI.
